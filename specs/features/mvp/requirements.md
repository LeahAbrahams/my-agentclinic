# מפרט MVP — Therapies, Appointments, Dashboard והקשחה

**Branch**: `feature/mvp`
**תאריך**: 2026-11-13
**סטטוס**: טיוטת מימוש; מבוסס על Roadmap הקורס ועל חזון הפרויקט

## בסיס היקף

- **מקורות**: `specs/mission.md`, `specs/techstack.md`,
  `specs/roadmap.md`, מפרט Agents and Ailments, ותוצרי Video 11
  ו-Video 12 במאגר הקורס הרשמי.
- **פריטי Roadmap שנותרו**: קטלוג Therapies וקשר לתקלות; קביעת Appointments;
  Dashboard לצוות; רספונסיביות ונגישות; טיפול ב-404/500 ולוג בקשות.
- **כלולים**: מענה מקומי, בדיוני וטכני לסוכני AI; דפי טיפולים ותקלות;
  בקשת פגישת שירות לסוכן; הצגת מצב וניהול סטטוס הפגישות בדף צוות; טיפול
  בשגיאות ובדיקות קבלה.
- **מחוץ לתחום**: מטופלים אנושיים, מידע רפואי, אבחון או ייעוץ רפואי, חשבונות
  משתמשים, הרשאות, אימייל, תשלומים, פרופילי מטפלים, דיווחים ופריסה בענן.
- **גילוי**: סריקת `specs/roadmap.md` ומפרטי Phase 1/2; פערי Phases 3–7
  ממופים למפרט זה.

## הכרעות והנחות

1. ה-MVP הקורסי יתאים לחזון הקיים באמצעות קליניקה בדיונית לתקלות AI בלבד.
   "טיפול", "פגישה" ו"צוות" הם שמות תצוגה עבור סיוע טכני לסוכן; אין לייצג
   אנשים כמטופלים או לשמור נתוני בריאות.
2. טיפולים הם פעולות תמיכה טכניות מומצאות, כגון בדיקת Prompt או סיכום
   הקשר. הם אינם טענות רפואיות או המלצות טיפול לאדם.
3. פגישה משויכת לסוכן AI ונושאת שם נותן שירות בטקסט חופשי, מועד וסטטוס.
   אין ישות מטפל/ת נפרדת. אין אימות משתמשים; Dashboard מיועד להדגמה מקומית
   בלבד, ואין לחשוף אותו לשימוש ציבורי.
4. נדרשים `agentId`, שם נותן השירות ומועד תקין. מועד נשמר ומוצג בעקביות;
   אין להוסיף כלל שאוסר מועד עבר, כי הוא לא הוגדר בקורס.
5. POST תקין יוצר פגישה ומפנה לעמוד אישור. קלט חסר/לא תקין אינו יוצר רשומה
   ומוצגת הודעת שגיאה בעברית. טקסט מוצג כטקסט מקודד; אין להריץ HTML שסופק
   בטופס ואין לשנות את משמעות הטקסט על ידי הסרת תגיות.
6. צוות ההדגמה יכול לשנות פגישה מ-`pending` ל-`confirmed` או `cancelled`;
   אין פעולת מחיקה. סטטוס שמגיע מחוץ לרשימה נדחה.
7. "תקלות בתהליך" ב-Dashboard הן תקלות שונות המקושרות לסוכנים פעילים.
   "פגישות פתוחות" הן פגישות בסטטוס `pending`.

## תרחישים ובדיקות

### סיפור 1 — בחירת מענה טכני (P1)

כמשתמשת, אני רוצה לעיין בפעולות סיוע טכניות ולראות מה מתאים לתקלה, כדי
להבין את אפשרויות התמיכה של סוכן בדיוני.

**בדיקה עצמאית**: פתיחת קטלוג התקלות, צפייה בפעולות הסיוע המשויכות, ופתיחת
קטלוג הטיפולים.

**תרחישי קבלה**

1. **בהינתן** נתוני הדוגמה, **כאשר** פותחים `/therapies`, **אז** מוצגות
   לפחות חמש פעולות עם שם ותיאור.
2. **בהינתן** תקלה בקטלוג, **כאשר** צופים בה, **אז** מוצגות פעולות הסיוע
   שהוגדרו עבורה.
3. **בהינתן** קטלוג ללא טיפולים או קישורים, **כאשר** פותחים אותו, **אז**
   מוצג מצב ריק בעברית ולא שגיאה.

### סיפור 2 — בקשת פגישת שירות לסוכן (P1)

כמשתמשת בהדגמה, אני רוצה לקבוע מועד שירות לסוכן AI ולראות אישור, כדי להשלים
את זרימת התמיכה.

**בדיקה עצמאית**: פתיחת טופס מתוך פרופיל סוכן, שליחה תקינה, וקריאת עמוד האישור.

**תרחישי קבלה**

1. **בהינתן** סוכן קיים, **כאשר** פותחים טופס פגישה, **אז** הסוכן מזוהה מראש.
2. **בהינתן** סוכן, נותן שירות ומועד תקין, **כאשר** שולחים, **אז** נוצרת
   פגישה אחת והדפדפן מנותב לעמוד אישור המכיל את פרטי הפגישה.
3. **בהינתן** קלט חסר, סוכן שאינו קיים או מועד לא תקין, **כאשר** שולחים,
   **אז** מוחזרת שגיאת טופס ברורה ולא נוצרת פגישה.
4. **בהינתן** טקסט ובו תגי HTML, **כאשר** הפרטים מוצגים באישור או בלוח,
   **אז** הטקסט מוצג בבטחה ואינו מופעל כ-HTML.

### סיפור 3 — מעקב וניהול פגישות צוות (P1)

כחברת צוות בהדגמה המקומית, אני רוצה לראות סיכומי פעילות ופגישות פתוחות,
כדי לעקוב אחר מצבן ולעדכן את הסטטוס שלהן.

**בדיקה עצמאית**: טעינת Dashboard, אימות ספירות, אישור פגישה וביטול פגישה.

**תרחישי קבלה**

1. **בהינתן** נתוני דוגמה ופגישה ממתינה, **כאשר** פותחים `/dashboard`,
   **אז** רואים מספר סוכנים, פגישות ממתינות ותקלות של סוכנים פעילים, לצד
   רשימות סוכנים ופגישות פתוחות.
2. **בהינתן** פגישה ממתינה, **כאשר** הצוות מאשר או מבטל אותה, **אז** הסטטוס
   נשמר והספירות והרשימה מתעדכנות.
3. **בהינתן** סטטוס שאינו נתמך או מזהה לא קיים, **כאשר** נשלחת בקשת עדכון,
   **אז** הנתון אינו משתנה ומוצגת תגובת שגיאה מתאימה.
4. **בהינתן** שאין פגישות פתוחות, **כאשר** נטען ה-Dashboard, **אז** מוצג
   מצב ריק בעברית.

### סיפור 4 — שימוש בטוח, נגיש ואמין (P1)

כמשתמשת, אני רוצה ניווט ודפים עקביים עם טיפול ברור בשגיאות, כדי שאוכל
להשלים את המסע גם בנייד ובאמצעות מקלדת.

**בדיקה עצמאית**: בדיקת דפי ה-MVP, טפסים, 404/500, תגובות לוג ופריסת נייד.

**תרחישי קבלה**

1. **בהינתן** כל דף בהיקף, **כאשר** מוצג, **אז** יש מעטפת בעברית/RTL,
   מבנה סמנטי, כותרות עקביות וקישורי ניווט עובדים.
2. **בהינתן** רוחב 375px או 1280px, **כאשר** נטען דף, **אז** אין גלילה
   אופקית והטופס והטבלאות נשארים שמישים.
3. **בהינתן** נתיב לא מוכר או שגיאת שרת, **כאשר** נשלחת בקשה, **אז**
   מוצג דף שגיאה מעוצב בעברית בלי Stack Trace.
4. **בהינתן** כל בקשת HTTP, **כאשר** היא מסתיימת, **אז** נרשמים method,
   path, status ומשך הבקשה בלי תוכן הטופס.

## מקרי קצה

- אין טיפולים, תקלות, קשרי המלצה, סוכנים או פגישות.
- `agentId` שגוי או חסר; מזהה פגישה לא קיים.
- שדות ריקים/רווחים בלבד, זמן לא ניתן לפענוח, ושם שירות עם תווי HTML.
- עדכון סטטוס לערך לא מוכר או פגישה שכבר בוטלה.
- שגיאת מסד נתונים, כשל בטעינת עמוד או נתיב לא מוכר.
- שם או תיאור ארוכים במסך צר.

## דרישות פונקציונליות

- **REQ-041**: המערכת MUST להציג ב-`/therapies` לפחות חמש פעולות תמיכה
  טכניות בדיוניות, כל אחת עם שם ותיאור.
- **REQ-042**: מערכת התוכן MUST לקשר תקלות לפעולות תמיכה ביחס רבים-לרבים.
- **REQ-043**: קטלוג התקלות MUST להציג את פעולות התמיכה המקושרות לכל תקלה.
- **REQ-044**: פרופיל סוכן MUST לספק קישור לטופס פגישה המזוהה עם אותו סוכן.
- **REQ-045**: טופס פגישה MUST לדרוש סוכן קיים, נותן שירות ומועד תקין.
- **REQ-046**: שליחת פגישה תקינה MUST לשמור רשומה יחידה ולהציג עמוד אישור
  לאחר הפניה; אין ליצור כפילות בעת טעינה מחדש של עמוד האישור.
- **REQ-047**: טופס פגישה פגום MUST להציג הודעת שגיאה בעברית ולא ליצור רשומה.
- **REQ-048**: פגישה MUST להתחיל בסטטוס `pending` ולהכיל מזהה סוכן, נותן
  שירות טקסטואלי, מועד וזמן יצירה; סטטוסים מותרים הם `pending`,
  `confirmed` ו-`cancelled`.
- **REQ-049**: Dashboard ב-`/dashboard` MUST להציג סך סוכנים, פגישות ממתינות
  ומספר תקלות פעילות של סוכנים פעילים.
- **REQ-050**: Dashboard MUST להציג רשימות סוכנים ופגישות ממתינות, וממשק
  לשינוי פגישה ל-`confirmed` או `cancelled`.
- **REQ-051**: שינוי סטטוס MUST לאמת מזהה וערך נתמך, לשמור את השינוי ולדחות
  קלט פסול בלי לשנות את הנתון.
- **REQ-052**: כל דפי MVP MUST להשתמש ב-Layout משותף בעברית וב-RTL, עם
  ניווט מעודכן, Header, Main ו-Footer.
- **REQ-053**: טפסים, רשימות וטבלאות MUST להיות שמישים ברוחב 375px ו-1280px,
  ללא גלילה אופקית; רכיבים אינטראקטיביים MUST להציג focus ברור.
- **REQ-054**: דפי היישום MUST להשתמש ב-HTML סמנטי, היררכיית כותרות עקבית
  ומסגרת מקומית ללא תלות CDN.
- **REQ-055**: נתיבים חסרים MUST להחזיר HTTP 404 ודף HTML מעוצב; שגיאות שרת
  MUST להירשם ולהחזיר דף HTML כללי שאינו חושף פרטים פנימיים.
- **REQ-056**: כל בקשת HTTP MUST להירשם עם method, path, status ומשך, בלי
  לרשום את גוף הטופס או ערכים רגישים.
- **REQ-057**: כל קלט טקסטואלי MUST להישמר ולהיות מוצג כטקסט; תגי HTML
  שסופקו בידי משתמש MUST לא להתבצע.
- **REQ-058**: טיפולים, פגישות ונתוני seed MUST לתאר שירות טכני בדיוני
  לסוכני AI בלבד, ללא נתוני בריאות של אנשים.
- **REQ-059**: עדכוני סכימה MUST להשתמש במיגרציות SQL סדרתיות, אטומיות
  וניתנות להרצה חוזרת; נתוני seed MUST להיות אידמפוטנטיים.
- **REQ-060**: לפני סימון המימוש MUST לעבור `npm ci`, `npm test`,
  `npm run typecheck`, `npm run build`, `npm audit`, בדיקות HTTP ודפדפן.

## ישויות מפתח

- **פעולת תמיכה**: שם ותיאור של מענה טכני בדיוני לתקלת סוכן.
- **קשר תקלה-פעולה**: קשר רבים-לרבים בין תקלה לבין פעולת תמיכה.
- **פגישה**: שירות מתוכנן לסוכן AI בדיוני, כולל נותן שירות, מועד וסטטוס.
- **סיכום צוות**: ספירות של סוכנים, פגישות ממתינות ותקלות המקושרות לסוכנים
  פעילים; נגזר מהנתונים הקיימים.

## תנאי הצלחה

- **SC-001**: משתמשת יכולה להגיע לקטלוג טיפולים מתוך הניווט ולזהות לפחות
  חמש פעולות וסיוע מומלץ לכל תקלה שיש לה קשר.
- **SC-002**: פגישה תקינה ניתנת ליצירה ולצפייה באישור אחד בלבד, וקלט חסר או
  לא תקין נדחה ללא רשומה חדשה.
- **SC-003**: כל שינוי סטטוס פגישה מאושר משתקף ב-Dashboard לאחר טעינה מחדש;
  קלט סטטוס פסול אינו משנה נתון.
- **SC-004**: בכל דפי MVP יש HTML סמנטי בעברית/RTL, ללא תוכן גולש אופקית
  ברוחב 375px או 1280px.
- **SC-005**: נתיב לא קיים ושגיאת שרת מחזירים HTML ידידותי; לכל בקשה נרשם
  סיכום תפעולי ללא גוף הטופס.
- **SC-006**: כל שערי הבדיקות ב-REQ-060 עוברים מסביבת תלות שנבנתה מחדש
  מ-Lockfile.

## שאלות/פערים

כהדגמה לימודית בדיונית לסוכני AI, בלי נתונים או ייעוץ רפואי אנושי.
